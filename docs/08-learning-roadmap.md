# 学习与改进路线

## 阶段一：理解确定性任务

运行 fixture 演示，手工核对样例；阅读 `contracts.py`、`source.py` 和 golden。

应能回答：为什么金额逐笔舍入？为什么先检查有效性再去重？为什么行 ID 不能用 order_id？CSV 数据记录与文本行有何区别？

完成标志：不用查看答案，也能写出一个新的有效/无效输入案例及其期望输出。

## 阶段二：理解闭环

阅读 `Harness.run`，跟踪第一次验收失败到第二次生成的参数；查看 `events.jsonl` 与每轮反馈。

应能回答：为什么退出码 0 不足以成功？验证器放在哪个进程？什么情况下应该停止？事件日志与断点恢复有什么区别？

完成标志：实现一个“先产生语法错误，再修复”的测试 backend，并验证未通过验收时没有 published。

## 阶段三：真实模型与环境

按教程分别跑通容器 fixture 和 Ollama。换用自己的模型，保留失败程序，分析它属于生成、执行还是业务规则错误。

应能回答：JSON Schema 结构化输出解决了哪些问题、还遗漏哪些问题？模型为何可能被样例误导？Docker 隔离实际挂载了什么？

完成标志：至少保存一次真实模型成功运行与一次失败运行的完整记录，补齐环境和版本信息。

## 阶段四：做一项自己的改进

从下面任选一项，先建立基线和测试，再修改：

- **反馈压缩：**对比只返回错误码、返回首个具体差异、返回完整差异的修复效果。
- **修复定位：**限制模型只修改受影响的转换函数，统计语义回归。
- **生成式数据案例：**构造边界数据，发现 oracle 或 worker 的遗漏。
- **多 profile：**加入一个新的业务任务，并明确复用部分与新增部分。

完成标志：有代码差异、原始实验数据、失败案例和能解释局限的报告。

## 简历之前

能从空白纸画出一次任务的数据流，解释核心函数，独立改一个规则并补测试，再按实际实验写简历。当前初稿的价值是降低启动成本；后续理解、修改和实验应形成你自己的工程记录。

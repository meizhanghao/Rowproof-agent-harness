# 扩展一个新任务

## 原则

框架可以复用；业务规则不能只靠改提示词来扩展。每个新 profile 应有独立规范、验证方法、golden 样例和失败案例。

## 示例方向：商品目录规范化

输入可能包含 SKU、名称、类目、价格，输出需要规范类目与字段。不要直接让模型自行定义“规范”；先给出允许的类目字典、字段映射与异常处理规则。

## 推荐步骤

1. **写任务说明。**新增 `docs/profiles/catalog-v1.md`，明确字段、顺序、异常原因、精度和记录保留条件。
2. **扩展契约。**新增 profile 对应的 Pydantic 模型和显式分派。当前 `TaskContract.profile` 是 Literal，必须修改代码；任意字符串不会自动获得支持。
3. **写输入适配。**定义行 ID 和输入读取边界，避免把订单固定列逻辑沿用到新数据。
4. **先写验证器。**用独立来源或人工核对的 golden 验证业务规则，不让候选程序决定验收标准。
5. **写候选协议。**更新 prompt 的输入输出规范及字段说明，保留可执行错误反馈。
6. **添加 fixture。**至少包含正确候选、表面成功但错误的候选、可修复候选。
7. **增加 CLI 分派与测试。**跑通错误检测、预算耗尽、正确发布以及不同 profile 不混用的测试。
8. **真实模型复现。**保存模型生成的失败案例，避免仅在 fixture 上调试。

## 验证器的选择

orders.v1 可以精确重算全部结果。复杂任务未必存在完整 oracle，可以使用可信参考数据、约束检查、变形测试或人工抽检，但必须在报告中说明哪些性质被验证，哪些仍然未知。

例如，打乱输入后汇总金额应保持不变，这是一种变形性质；但有“首条有效去重”规则时，随意打乱重复记录可能改变被保留值，因此不能直接套用排列不变性。

## 后续可替换部件

- 接入其他模型：实现 `CodeBackend`，保持模型代码必须隔离执行。
- 接入 LangGraph：把现有阶段封装为节点，沿用独立验证器；新增持久化语义需要测试。
- 接入 MCP：将受控数据操作封装为 MCP 工具；MCP 只是接口，不能替代验收。
- 支持 pandas：准备固定依赖镜像、更新代码生成协议、比较收益与资源成本。

以上都是扩展方案，首版没有将其声明为已实现功能。

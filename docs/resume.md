# 简历描述与面试说明

以下文字对应本项目的实现方向。起止时间请填实际开发时间；先完成复现、理解和自己的修改，再用于正式求职。不要将 fixture 的预设修复写成真实模型效果。

## 可使用的项目介绍初稿

**[实际起止时间]　基于数据契约与执行反馈的数据处理 Agent Harness（个人项目）**

**背景介绍：**针对数据处理 Agent 生成的脚本虽正常运行、但可能遗漏记录或产生错误统计的问题，构建以数据契约和独立验收为核心的执行闭环，支持候选代码执行、错误反馈、有限次修复及验证后工件发布。

**技术栈：**Python、Pydantic、Decimal、Ollama API、Docker、unittest、JSON Schema、GitHub Actions 配置。

**项目实现：**

1. **数据契约建模：**使用 Pydantic 定义字段规范、金额精度、日期格式、首条有效记录去重及执行预算，导出 JSON Schema，统一候选程序的输入输出协议。
2. **独立结果验收：**实现基于源数据的业务 oracle，逐条核对保留记录、拒绝原因及汇总金额，通过数据血缘记录识别静默丢行和伪造统计，避免仅依赖程序退出码判断成功。
3. **反馈执行闭环：**设计生成、执行、验收、修复等显式状态，向生成后端反馈结构化错误，并设置尝试次数、执行超时及日志限制；提供 Ollama 生成适配器和 Docker 执行适配层。
4. **工件与实验管理：**保存每轮代码、执行日志、验收结果和事件记录，验收通过后校验文件哈希并发布完整工件；构建“仅退出码、只验收、验收并修复”三类脚本化对照实验及自动化测试。

## 更短的简历版本

围绕数据处理 Agent 构建“契约—执行—验收—反馈修复”闭环：基于 Pydantic 约束业务规则，独立核对清洗结果、逐行追踪记录与金额汇总；实现有限次修复、执行预算、事件追踪及验证后工件发布，并提供 Ollama/Docker 适配层与可复现实验。

## 建议准备的追问

1. 规则已经确定，为什么不用普通 ETL？——当前 CSV 任务用于精确检验 Harness；固定任务直接 ETL 更简单。模型价值应在后续新转换任务中验证。
2. Schema 通过为什么还要业务验收？——Schema 不能证明该保留的订单都被保留，也不能证明业务口径正确。
3. 为什么拒绝行也要记录？——让每条源记录有明确去向，发现通过删除记录绕过校验的行为。
4. fixture 和真实 Agent 有什么区别？——fixture 的错误及修复是预设程序；真实后端根据反馈生成代码，效果需单独实验。
5. 文件哈希是不是防篡改？——只能检查与记录的一致性，没有签名或可信存储就不能提供完整防篡改保证。
6. JSONL 是否等于断点恢复？——不是，首版没有恢复调度及外部操作幂等协议。
